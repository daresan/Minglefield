## What was built

The separate `Minglefield` Rust binary (on Windows `Minglefield.exe`)
is produced from `installer/crates/installer-cli/src/minglefield_app.rs`.
It is a different entrypoint from `minglefield-installer-cli` and does
not require the Setup Manager, a running installer process, user-installed
Python, Conda, Git, Cargo, or a source checkout at application launch.

The single developer/CI command for this OS-native application package is:

```sh
cd installer
python -B scripts/build_native_alpha_application.py --output /absolute/new-native-minglefield
```

The **build machine**, not the end user's machine, uses Rust and Python to
compile the OS-native executable and assemble exact pinned CPython 3.11,
SQLCipher, audited package dependencies and the existing Alpha application.
All managed files, **including the native binary**, are SHA-256 inventoried.
The native application manifest records the binary and the OS-specific
runtime paths. An unrecognized, missing or modified managed file prevents
application launch. At this stage the inventory hash is self-declared in
the package and is **not** a publisher signature.

Windows places `Minglefield.exe` at the managed application root.
Linux and the raw macOS payload place `Minglefield` at that root. The new
macOS packaging step wraps the **unchanged managed payload** in
`Minglefield.app/Contents/MacOS/`, with a Finder-recognizable
`Contents/Info.plist`. The application binary still finds its inventory,
embedded runtime and private Alpha worker relative to its own executable.

After building the managed native payload on macOS, create an independently
verified `.app` directory using:

```sh
python -B scripts/package_macos_alpha_app.py \
  --source /absolute/native-managed-alpha \
  --output /absolute/unused-folder/Minglefield.app
```

The output path must be an unused `Minglefield.app` name in an existing
directory. The runtime manifest's macOS OS identifier is `darwin-` (Python's
`platform.system().lower()`), not `macos-`. The script rechecks the
SHA-256 managed inventory and preserves
relative runtime links; it never places a database, credential, Host token
or autogenerated plaintext config in the bundle. The destination is
reserved exclusively and is never silently overwritten or deleted.
`--probe-exit --no-browser` checks that the native executable launches
from `Contents/MacOS` with an already initialized encrypted database;
the macOS native CI gate exercises this exact bundled restart.

**This proves bundle structure and CLI-controlled embedded startup only,**
not Finder/double-click usability, a graphical DB chooser/password prompt,
Apple code signing, notarization, Gatekeeper acceptance or a release DMG.
Those remain M2.10/M2.14 requirements. Linux desktop packaging is likewise
still pending. The runtime directory and its managed files must remain together.

## Desktop startup file/password dialogs (implemented; CI-tested logic)

For ordinary launch **without a complete selected SQLCipher database and key**,
the existing native Minglefield executable now requests only the missing
items using operating-system GUI dialogs. An administrator can open
`Minglefield.exe` on Windows or `Minglefield.app` on macOS without typing
Python commands. The database chooser selects an **existing** file; the
password is entered into a masked field. The native executable still checks
its pinned file inventory and SQLCipher unlock and starts the existing
loopback Alpha gateway; a Minglefield user then signs in separately with
their account password. The dialogs do not create a fresh DB, reset a
password, or grant Host rights.

Windows uses the OS Windows Forms picker and masked text field through
a fixed PowerShell program; macOS uses the system's file and hidden-answer
dialogs through fixed `osascript` programs. On Linux the launcher uses an
already installed `zenity` or `kdialog` from fixed OS locations; absence
fails closed, with no implicit package installation. The dialog commands
never interpolate a SQLCipher password, database path, account credentials
or user-supplied shell input into a command line. Passwords are returned
only through an inherited pipe and never persisted in generated config.

The shared Bee-like administrator-provided CLI options still take precedence:
if a database is selected in the explicit/owner-authored version-3
config, it is not selected a second time; if a password is supplied by an
approved config field, argument, file, environment variable or private
stdin, it is not prompted for again. Automation operations
`--verify-only`, `--probe-exit`, `--no-browser`, `--secrets-stdin` and
explicit `--no-dialog` never open a UI. An intentional Cancel exits
without an additional warning dialog. A failed *graphical* unlock can
display one fixed, secret-free desktop warning message; raw paths, keys
or backend errors are never used in its command arguments.

## Direct native launch, without the installer

For an **existing, individually owned encrypted Alpha database** that has
already completed normal first-run account initialization:

```sh
# On Windows PowerShell (inside the installed application directory):
.\Minglefield.exe --database "D:\private-data\minglefield.db" --db-password "owner-chosen-key"

# On Linux/macOS (inside the installed application directory):
./Minglefield --database /absolute/private-data/minglefield.db --db-password 'owner-chosen-key'
```

The administrator may supply the SQLCipher key using `--db-password`,
`--db-password-file`, `MINGLEFIELD_DB_PASSWORD`, a full version-3
installer-compatible `--config` text file, or `--secrets-stdin` with a
bounded `{"db_password":"..."}` JSON frame. If the owner **chooses** to
provide a file called `minglefield.conf` next to the executable, the
application loads that version-3 configuration automatically. The
installer never generates a plaintext-password config by default.
As with the approved Bee-style contract, owner-supplied argv, environment,
configuration files and password files are permitted but do not appear in
Minglefield-generated logs, readiness messages or error diagnostics.

The executable validates its own inventory and the encrypted database
using the shared Rust SQLCipher inspection, then starts the existing
`application/server/installed_alpha_launch.py` worker via a **private
stdin request**, entirely inside the installed runtime. It refuses
plaintext/invalid databases and does **not** create, claim or reset any
user/Host. The worker must return exactly the approved loopback readiness
frame for `127.0.0.1`; the remote Host claim bootstrap remains disabled.
The native app then opens the installed Alpha web UI in the OS browser.
The user still logs in normally with a **separate account password**.

Developer/CI-only checks: `--verify-only` validates inventory and
SQLCipher key without launching the gateway; `--probe-exit --no-browser`
starts and probes the gateway over 127.0.0.1 and stops its worker before
exiting. The cross-OS integration script
`scripts/verify_cli_local_setup.py --package <managed-root> --require-native`
installs the real package, creates a **disposable** encrypted DB/Host,
verifies normal and invalid login credentials, launches the native
executable, checks its loopback contract, restarts using an
owner-authored config, refuses setup replay and refuses tampered app
payloads. It does not access private user DBs.

## Remaining required product acceptance

The application-owned database chooser and masked SQLCipher password
dialog are implemented, but their **actual visual interaction, cancellation,
focus, error notifications and double-click startup** have not been
independently accepted by a user. The current native binary remains a
working executable and a first desktop adapter, **not** the final polished
shell. macOS Finder interactive acceptance/signing/notarization, Linux
desktop packages, Windows console-window UX, application process
shutdown/restart controls, publisher
signature/release integrity, independent portable artifacts, GUI/silent
installer integration and installed-user acceptance on Shadow remain
unfulfilled. The official/fork source-build mode remains a mandatory
**later** installer expansion. None of these gaps grants permission to
bypass database ownership or the original Host-first-run policy.
