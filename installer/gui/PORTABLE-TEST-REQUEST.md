# Portable GUI milestone — values-only editor and explicit registered schema-object evidence

**2026-11-05 — next owner-authorized one-time Shadow test build** on
`feat/game-integration-updates`. Updating this existing milestone marker is
the designated explicit trigger for separate Windows, Linux and macOS
portable GUI builds. Routine feature commits do not trigger packaging.

## Change scope and security invariant

This milestone fixes two discrepancies reported by the owner:

1. The *Validated Installation Plan* previously showed
   `database.schemaAssessment` for 27 tables and 111 columns but lacked
   the separately expected `database.schemaObjectAssessment`.
   The old rehearsal's `schemaObjectCount:31` and
   `verifiedSchemaEntryCount:58` are snapshot-fidelity counters, not
   independent proof of the registered full-schema object audit.
   Both the validated plan and Step-6 database summary now use
   `databaseReviewEvidence()` for exactly the same two assessments.
   The validated plan includes a distinctive,
   `database.reviewContract:"sqlite-existing-values-only-schema-objects-v2"`
   marker; its absence means the plan was not generated by this GUI
   revision and a previous EXE or entrypoint should be investigated.
   Step-3 inspection additionally displays the separate object-audit
   reason and matched/expected entry counts. An incomplete backend
   audit must be reported explicitly as unverified.
2. Data review must allow changes to **existing stored values only**,
   never editing a column definition or changing SQLite storage types.
   The type dropdown has been replaced by a read-only type label.
   Existing non-NULL values can be changed within their original
   TEXT/INTEGER/REAL/BLOB storage class; NULL values remain NULL.
   JS staging and full-row diff validation reject kind changes;
   Rust migration core independently rejects kind transitions even
   when a crafted client bypasses the GUI. No SQLite schema mutation
   is allowed by this editor.

The five data areas remain Anmeldung, Hosts, Effekte, Jobs and Games;
unmapped extension tables remain accessible as a fallback.
Comfy workflow JSON stays in SQLite.

The read-only migration, temporary encrypted SQLCipher copy, integrity
proofs, wrong-key rejection and temporary-file removal remain intact.
The source database must not be modified, the final destination must
not be created, and `migrationEnabled`, `executionEnabled`,
`encryptedDestinationVerified`, `destinationCreated` must all
stay **false**. This is a portable setup-manager preview, not yet
an operational installation.

## CI requirements

- Installer Rust checks on Windows, Linux and macOS: rustfmt,
  check, Clippy and full Rust tests including typed-cell rejection.
- Tauri GUI checks on all three platforms: Node tests,
  frontend bundle, Rust backend compile/lint/tests.
- Explicit tests for no mutable type dropdown, same-kind value edits,
  invalid-value rollback, immutable kind at JS and Rust boundaries,
  schema-audit contract in validated-plan evidence, and explicit
  failure when backend object proof is absent.
- Generate the Windows EXE, Linux AppImage and macOS app from this
  exact milestone marker commit. Do not reuse older artifacts.

## Shadow acceptance criteria

1. Download `tauri-portable-windows-exe` from this exact GitHub
   Actions milestone build. Extract it to a **new directory**, rather
   than launching an older extracted EXE with the same filename.
2. Inspect the existing `alpha.sqlite3` in Step 3, then validate the
   complete installation plan.
3. Confirm `database.reviewContract` equals
   `sqlite-existing-values-only-schema-objects-v2`.
   The plan must contain `database.schemaObjectAssessment` in
   addition to the column `schemaAssessment`. On a matching
   registered source DDL this should report
   `verified:true`,
   `reason:"registered_alpha_schema_objects_verified"` and
   `matchedSchemaEntryCount == expectedSchemaEntryCount`.
   If it is unverified, share only its reason and missing/extra/
   incompatible object **names** for analysis, never row values.
4. Open Hosts or Effekte, select a table, verify that cells have a
   **read-only type label rather than a type dropdown**.
   Change one ordinary existing TEXT value or INTEGER value, switch
   tabs and return to verify the edited value is retained.
5. Run the in-memory rehearsal and temporary on-disk SQLCipher copy.
   Verify the edit counts match, the ciphertext and wrong-key checks
   pass, temporary files are removed and no durable target is created.
6. Confirm no schema columns/types were altered, no source writes,
   no direct execution and no credentials in plan output.

31 preserved non-table schema objects + 27 application tables = 58
schema entries on the owner's previously tested source. Those counts
alone never substitute for a positive registered object assessment.

Durable encrypted destination migration, operational SQLCipher runtime
integration and authenticated first-run host provisioning remain
separate gates requiring explicit later verification.
